# 因果模型：不要把症状叫作根因

根因分析的产物不是一条无限向上的“为什么”，而是一组有边界、有证据、能指导纠正的因果主张。

## 因果角色

### Symptom

用户、测试、监控或下游组件观察到的失败。它描述“发生了什么”，不解释为什么。

### Trigger

让潜伏问题显现的输入、状态、负载、事件顺序、版本或环境条件。触发器可以是必要条件，但不一定本身错误。

### Failure mechanism

错误状态怎样生成、传播并产生可见失败。例如：重复消费使副作用执行两次；失效缓存让数据库连接池耗尽；错误生命周期在对象销毁后继续回调。

### Proximate cause

紧邻失败、直接产生结果的事件或条件。消除近因可能让当前症状消失，但未必防止同类故障复发。

### Root/systemic cause

在明确系统与时间范围内，最早可控、能解释机制、纠正后可阻止该类故障复发的因素。它可以位于实现、契约、框架集成、设计、架构或运行环境层。

### Contributing factor

增加故障概率、持续时间或影响，但单独移除不足以阻止复发的因素。

### Missing barrier / escape cause

本应预防、隔离或更早发现故障却不存在或失效的控制，例如类型/模型约束、契约测试、故障隔离、监控、发布门禁或回滚能力。

## 二维标注

每个节点同时标注“因果角色 × 系统层”，不要强迫整场故障只有一个层级：

```text
流量峰值              = Trigger × RUNTIME_ENVIRONMENT
客户端与服务共同重试  = Contributing factor × SYSTEM_ARCHITECTURE
重复扣款              = Symptom × observable behavior
缺少幂等所有者        = Root cause × COMPONENT_DESIGN / CONTRACT
没有重复消息测试      = Missing barrier × verification process
```

一个组件看到的 cause 可能是上游组件的 symptom。继续追踪到“谁最早有能力阻止错误状态”。

## 因果链模板

```text
在 <trigger/conditions> 下，
<origin owner/layer> 的 <contract/invariant/assumption> 被 <cause> 破坏，
产生 <first invalid state>，
经由 <propagation mechanism> 传播，
最终表现为 <symptom/impact>。
<contributing factors> 放大了概率或影响，
而 <missing barriers> 没有预防或及时发现它。
```

## 根因充分性检查

### 解释覆盖

它是否同时解释关键失败事实、成功对照、时间线和影响范围？只解释一条日志不够。

### 可区分性

它与其他有竞争力的假设是否产生不同预测？如果任何结果都能被解释，假设不可证伪。

### 反事实

保持主要条件不变，控制、移除或替换该因素后，故障是否按预测消失或改变？生产环境无法安全实验时，可以由完整静态路径、历史自然实验或版本矩阵提供较弱的反事实证据。

### Incorrectness

为什么这个因素本身是错误的？必须指向明确契约、规范、不变量或质量属性。仅仅与失败相关不等于错误。

### Recurrence scope

纠正它能防止哪些等价输入、路径和故障？若只能覆盖当前样本，它更像特判。

### Control boundary

该因素是否在系统可控制范围内？外部故障可能无法消除，但系统对外部故障的假设、隔离和降级策略仍可成为设计原因。

## 结论强度

- `CONFIRMED`：有可复现反事实，或代码/数据/控制流与契约构成闭环。
- `PROVISIONAL`：最能解释当前证据，主要替代解释已检查，但关键反事实因安全、环境或数据限制不可完成。
- `INCONCLUSIVE`：失败契约、关键证据或区分实验不足。

置信度属于每条因果主张；复杂故障中可以同时有 confirmed mechanism、provisional systemic cause 和 unknown contributing factor。

## 常见因果谬误

- **报错位置谬误**：异常抛出处就是根因。
- **最近改动谬误**：时间相关自动等于因果。
- **旧故障复用**：以前是 X，所以这次也是 X。
- **单因幻想**：复杂系统必须有唯一、最深的根因。
- **架构拔高**：修复困难或改动大，所以一定是架构问题。
- **环境甩锅**：只在生产出现，所以与代码/设计无关。
- **人因终止**：以“操作失误”结束，而不问系统为什么允许危险状态。
- **测试转绿谬误**：某个改动让测试通过，所以它证明了根因。

“为什么”用来展开因果链，“什么、在哪里、在什么条件下”用来约束它。不要用固定次数的 Five Whys 代替证据。
