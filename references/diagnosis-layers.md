# 根因层级判定

层级不是严重度排名。局部实现错误可以造成严重事故，架构问题也可能只在边缘场景出现。目标是把纠正放到最早拥有相关不变量、能关闭整类故障路径的位置。

## IMPLEMENTATION · 实现层

适用条件：

- 契约、状态所有权和组件设计已经明确且合理。
- 某个局部计算、分支、状态转换、资源清理或错误处理偏离既有规则。
- 纠正可以由当前责任所有者完成，不要求其他组件改变契约或拓扑。

证据门槛：

- 隔离复现或闭环静态路径。
- 找到 expected 与 actual 第一次分叉的位置。
- 局部纠正能覆盖所有等价入口，而非单个样本。

不要因为代码只有一行就自动归为实现层；一行也可能暴露缺失契约或状态所有权。

## CONTRACT · 契约与不变量层

适用条件：

- 生产者和消费者对输入、输出、错误、版本、时序、幂等、事务或生命周期存在不一致理解。
- 契约未写明，或现有契约无法表达业务不变量。
- 各方局部实现看似合理，组合后却产生失败。

证据门槛：

- 边界两侧的真实数据、调用行为和期望。
- 规范、类型、schema、文档或实际消费者约束。
- 证明不是一方单纯违反了已经明确的契约。

纠正通常需要在拥有边界的地方定义并执行契约，再用 producer/consumer 或属性测试固定它。

## FRAMEWORK_INTEGRATION · 框架集成层

适用条件：

- 故障与框架生命周期、调度模型、资源所有权、默认配置、扩展点、缓存、ORM/session、渲染或依赖注入语义有关。
- 应用对框架的 mental model 与真实执行模型不一致。

先区分两种情况：

- **误用/错误集成**：公开契约明确，但应用违反它；通常由当前项目纠正。
- **框架缺陷/回归**：应用遵守受支持用法，框架仍无法满足契约。

宣称框架缺陷至少需要：

- 最小、受支持的复现。
- 版本矩阵或绕过框架的对照。
- 官方文档、源码、release note 或上游 issue 证据。

没有这些证据时，不用“框架问题”代替不理解生命周期。

## COMPONENT_DESIGN · 组件设计层

适用条件：

- 单个组件内部没有清晰的状态所有者、生命周期或不变量执行点。
- API/抽象迫使多个调用方重复 guard、转换、重试或补偿。
- 数据模型允许无效状态，算法/职责分配让同类错误自然复发。
- 局部实现都符合当前设计，但设计本身无法稳定实现需求。

证据门槛：

- 同源问题跨多个路径、调用方或历史修复重复出现。
- 依赖/状态图说明不变量无法在现有责任边界一次执行。
- 候选设计能在相同场景下提供可验证的单一所有权或约束。

设计问题仍可能通过很小的改动纠正；改动规模不是层级判据。

## SYSTEM_ARCHITECTURE · 系统架构层

适用条件：

- 根因来自跨组件拓扑、共享数据、耦合、依赖方向、信任边界、故障域、一致性或协调模型。
- 正确行为要求改变组件责任、公共契约、状态所有权或系统质量属性策略。
- 局部纠正只会把故障移动到另一个组件，或改善一个质量属性却破坏另一个。

架构结论至少需要：

1. 端到端关键流、依赖关系和爆炸半径。
2. 一个具体质量属性场景：

```text
刺激来源 → 刺激 → 环境 → 被影响对象 → 期望响应 → 可测响应
```

3. 当前架构的敏感点、权衡点和失败机制。
4. 为什么现有组件边界内没有责任所有者能独立关闭故障路径。
5. 候选方向在同一场景下怎样改善可测响应，以及引入什么新权衡。

“系统很复杂”“修了很多次”“需要重构”或“代码分散”都不足以证明架构缺陷。

## RUNTIME_ENVIRONMENT · 运行环境层

适用条件：

- 配置、权限、资源、网络、文件系统、时间、区域、版本、工具链、部署或外部依赖差异是故障必要条件。
- 相同 artifact 在受控环境对照中表现不同。

证据门槛：

- 环境 diff、版本/配置证据和遥测。
- 受控复现、故障注入或自然实验。
- 明确运行边界：环境是否违反已声明前提，还是只触发了系统本应处理的条件。

若环境变化在支持范围内，却能让系统进入无效状态，环境可能只是 Trigger，真正根因仍在契约、设计或架构层。

## MISSING_BARRIER · 缺失屏障

测试、监控、类型约束、代码审查、发布门禁、隔离和回滚能力解释“为什么问题没有更早被阻止或发现”。它们通常是 escape cause，而不是替代技术根因。

记录：

- 哪个屏障本应介入。
- 它不存在、覆盖不足、失效还是结果未被处理。
- 加强它能预防缺陷，还是只能提前发现。

不要用“开发者没写测试”结束分析；先说明什么技术不变量需要被测试，以及哪个边界拥有它。

## 分层判定顺序

1. 找到首个错误状态，而不是最后报错位置。
2. 找到最早拥有相关不变量并能预防错误的责任边界。
3. 判断纠正是否需要改变其他组件的契约、责任或系统拓扑。
4. 用区分实验验证候选层，不按文件位置和改动规模猜测。
5. 同时记录 Trigger、Contributing factor 和 Missing barrier；不要让一个标签吞掉完整因果链。

推荐输出：

```text
Primary causal claim: <cause>
Causal role: <root / contributing / trigger / escape>
System layer: <one of the layers>
Owner/invariant: <who can prevent it and what must hold>
Evidence: <closed causal path>
Rejected layers: <alternatives and why>
```
