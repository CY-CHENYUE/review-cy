# 系统化排查工作流

这份 reference 用于回答“接下来应该看什么、做哪个实验”。目标是提高信息增益，而不是把所有调试工具机械跑一遍。

## 1. 保存原始事实

在任何修改之前记录：

- 完整错误、stack trace、日志时间范围和 trace/request/job ID。
- 输入、用户/租户、数据状态、版本、commit、依赖与配置摘要。
- 预期、实际、影响、频率和首次/最后出现时间。
- 失败前后发生的代码、配置、发布、流量、数据和基础设施变化。
- 已尝试的修复、实验及结果，包括没有效果的尝试。

不要只复制错误最后一行，也不要先格式化、清理或重跑到证据消失。

## 2. 建立失败与成功对照

理想对照只差一个关键变量：

| 维度 | Failing case | Passing control |
|---|---|---|
| 输入/状态 |  |  |
| 代码/版本 |  |  |
| 配置/权限 |  |  |
| 负载/时序 |  |  |
| 依赖/外部服务 |  |  |
| 运行环境 |  |  |

如果差异很多，先用输入缩减、配置二分、`git bisect`、组件替身或最小复现降低维度。缩减后的案例必须仍代表原故障，不能把失败机制一起删掉。

## 3. 从可见失败反向追踪

从用户看到的结果向上游追踪：

1. 最终失败发生在哪里？
2. 该位置收到了什么错误值、状态或事件顺序？
3. 谁创建或传入它？
4. 正确值第一次变成错误值的边界在哪里？
5. 哪个组件拥有防止该转换的能力和责任？

同时做正向验证：从入口沿正常路径跟踪数据、控制流和状态变更，确认反向推理没有跨过隐藏的转换、缓存、事务、重试或异步队列。

## 4. 多组件系统的边界取证

对每个相关边界记录：

```text
component A output
  → serialized/request/event form
  → transport/config/context propagation
  → component B input
  → B state transition and output
```

核对：

- 数据值、类型、版本和顺序是否保真。
- 身份、权限、locale、时区、事务和 trace context 是否传播。
- timeout、retry、cache、queue、backpressure 和部分失败是否改变语义。
- 涉及 cache 时，分别记录每一层的 key/namespace、generation、命中来源和 write/invalidate/refill/read 时序，不用一次“清缓存”同时改变多层状态。
- 生产者认为“已成功”时，消费者是否已经持久化或只接收了请求。

可在安全环境加入最小观测点，但不要泄露秘密或敏感数据。观测行为可能改变并发、性能和时序，应记录这个混杂因素。

## 5. 优先选择区分实验

好实验不是“再跑一次”，而是让竞争假设产生不同预测。

选择顺序：

1. 低风险、低成本、能排除最多假设的只读检查。
2. 可逆的单变量实验。
3. 隔离环境中的版本、配置、负载或故障注入对照。
4. 只有必要时才在生产系统做受控干预。

实验前写下：

```text
If H1 is true, experiment E should produce O1.
If H2 is true, the same experiment should produce O2.
Side effects/confounders: ...
Rollback/cleanup: ...
```

实验后记录实际结果，不重新解释预测来迎合结果。

## 6. 常用定位策略

### Recent changes

检查 recent diff、依赖、配置、schema、数据形状、运行时和流量变化。时间接近只说明值得调查；必须证明变化能产生当前机制。

### Bisection

对版本、输入、配置、组件链或时间线二分。每一步都要有稳定的 failure oracle，否则二分结果没有意义。

### Working example comparison

在同一代码库或官方参考中寻找相似的正常路径，完整比较生命周期、依赖、默认值、状态所有权和清理行为。不要只复制看起来不同的几行。

### Data/control-flow tracing

跟踪坏值、错误事件顺序、资源句柄和副作用的来源。异步系统同时追踪逻辑因果与真实发生时间，避免把日志顺序当作执行顺序。

### Load and failure experiments

性能、并发与分布式问题需要在代表性负载、部分失败、重试和资源上限下观察。happy path 通过不能排除反馈回路、竞争条件或爆炸半径。

## 7. 保留阴性结果

记录被排除的假设、实验和证据，防止后续 Agent 重走同一路径。阴性结果至少应说明：

- 原假设及预测。
- 实际观察。
- 是否存在混杂因素。
- 结论是 `REJECTED`，还是仅因实验无效保持 `OPEN`。

没有观察到预期结果不一定反驳假设；也可能是观测点、样本或实验设计不足。

## 8. 停止条件

在以下状态之一停止当前诊断回合：

- 已形成 `CONFIRMED` 因果闭环。
- 已形成 `PROVISIONAL` 模型，进一步反事实实验在当前权限/风险下不可行。
- 关键证据耗尽，竞争假设无法区分，必须返回 `INCONCLUSIVE`。
- 用户只授权了某个范围，继续调查会越界。

“已经看了很久”或“有一个听起来合理的解释”不是停止条件。
