# 专项诊断镜头

只加载与当前证据有关的镜头。它们帮助生成假设，不自动产生根因结论。

## 状态、所有权与生命周期

- 关键状态由谁创建、修改、持久化、缓存、失效和销毁？
- 是否存在多个事实来源、隐式全局状态、派生状态回写或跨层同步？
- 不把“缓存”当成一个整体：逐层记录权威源、cache key/namespace、值的 generation/version，以及 write、invalidate、refill、read 的逻辑时序。若权威源已推进而某一层仍返回旧 generation，支持该缓存边界假设；若各层 generation 一致但消费者仍旧，转查任务快照/对象生命周期；若旁路某层不改变结果，降低该层嫌疑。
- 状态机是否允许业务上无效但类型上合法的组合？
- 初始化、ready、active、closing、closed 等阶段是否可区分？
- cleanup、取消、异常退出和重复调用是否保持不变量？
- 错误处理发生时，状态已经提交到哪里？

框架回调、资源泄漏、重复订阅和“偶尔为空”往往需要先回答生命周期与所有权，而不是先加 guard。

## 并发、异步与分布式交互

- happens-before 关系是什么，日志时间是否等于逻辑因果顺序？
- 哪些操作可重入、重复、乱序、延迟或并发执行？
- 副作用的幂等键、事务边界和唯一所有者在哪里？
- retry 是独立还是多层叠加，是否有 backoff、jitter、budget 和终止条件？
- 部分成功、超时后成功、消费者崩溃重放怎样处理？
- 缓存、队列和数据库分别提供什么一致性保证？
- 锁保护的是同一份状态吗，跨进程/服务是否仍成立？

固定 sleep 让测试稳定，通常只改变竞争窗口，不证明竞态根因消失。

## 数据、schema 与一致性

- 数据在哪个边界第一次变成无效、过期、不完整或歧义？
- schema、业务不变量和数据库约束是否一致？
- migration/backfill 与旧新版本共存时的读写矩阵是什么？
- 是否存在双写、异步复制、缓存失效或历史数据兼容窗口？
- 删除、重放、恢复和回滚是否可证明？
- 多租户、权限、时区、locale、编码和精度是否属于数据契约？

在读取处补默认值可能掩盖写入或迁移边界已经失守。

## 性能、资源与退化

- 性能 oracle 是延迟、吞吐、资源、队列长度还是用户成功率？
- 基线与退化场景的负载、数据量、并发和缓存状态是否可比？
- CPU、内存、连接、文件句柄、线程、队列或外部 quota 在哪里饱和？
- 症状是根资源耗尽，还是上游反馈回路造成的次生饱和？
- 是否存在 chatty I/O、无界 fan-out、N+1、retry storm、锁竞争或资源生命周期错误？
- 优化是否只把瓶颈移动到下一层？

扩容可以 containment，但若需求增长必然再次触顶，它不自动构成 root correction。

## 框架、依赖、构建与运行环境

- 应用对 framework lifecycle、scheduler、thread model、DI scope、ORM session 或 render/effect 语义的假设是什么？
- 官方契约、reference implementation 和当前版本真实行为是否一致？
- 依赖升级、默认值、feature、ABI/API 或 lockfile 是否变化？
- 本地与 CI/生产的 artifact、架构、环境变量、权限、文件系统、shell、locale、时区、证书和网络是否一致？
- build cache、generated files、conditional compilation 和 toolchain discovery 是否可重现？
- 用最小受支持项目能否复现，版本矩阵在哪里出现分叉？

只有应用遵守公开契约仍失败时，才把“框架自身缺陷”列为主要原因。

## API、协议与跨消费者契约

- 字段、错误码、顺序、版本、可选性和默认值是否有明确语义？
- producer 何时认为成功，consumer 何时实际完成？
- 向后/向前兼容、灰度、双版本和未知字段怎样处理？
- timeout、取消、分页、重试和幂等是否跨边界一致？
- 是否存在当前仓库之外的消费者、脚本、移动端或人工流程？
- contract tests 是验证真实消费者，还是只验证 provider 自己的理解？

若所有调用方都“正确”但理解不同，根因通常不在某一个 if，而在契约或设计层。

## 安全与信任边界

- 身份、授权对象、tenant、角色和资源所有权在哪里绑定？
- 不可信输入经哪些解析、规范化、反序列化、模板、SQL 或命令边界？
- 校验发生在可信转换之前还是之后，是否能被另一入口绕过？
- secrets、token、权限和审计上下文怎样传播与失效？
- fail-open、默认允许、缓存授权和 confused deputy 是否存在？

安全问题可以是实现错误，也可能源于对象级契约、状态所有权或信任边界架构；用因果证据决定层级。

## 测试、监控与工程屏障

- 原故障对应哪条不变量，现有测试为什么没有表达它？
- 测试是否会在实现错误时真正失败，是否依赖 sleep、顺序或共享环境？
- 监控观察用户症状、内部原因还是容易误导的代理指标？
- 告警、日志和 trace 能否关联到同一请求/状态转换？
- 发布门禁是否绑定当前 artifact/commit，失败结果是否被处理？
- 是否有近失事件、相同 bug 聚类或重复人工步骤？

这些通常解释 escape 和 recurrence，不应替代对技术 failure mechanism 的分析。
